# Vault Check

**A public, keyless reserve check for NEAR Intents: does what the contract owes its users still match what it actually holds?**

[한국어](README.ko.md) · Built for [NEAR HACKATHON](https://nearhackathon.com) (November 2026). Tracks: `open`, `defi`, `security`.

**Watch the replay:** [https://lee2017-bit.github.io/near-vault-check/](https://lee2017-bit.github.io/near-vault-check/) (45 s, runs in the browser) · [full report](https://lee2017-bit.github.io/near-vault-check/report.html)

## The problem

NEAR Intents keeps every user's deposit inside one contract, `intents.near`, as an internal ledger (NEP-245 multi-token).
The real tokens sit on each token's own contract, in the balance of `intents.near`.
For every token the ledger must stay backed:

```
ledger(token) = intents.near.mt_supply(token)                  what Intents owes all users
vault(token)  = <token contract>.ft_balance_of / mt_balance_of(intents.near)   what it holds
invariant:      ledger <= vault
```

On 29 Sep - 1 Oct 2026 a deposit-notification bug let an attacker create $3.8M of "ghost" USDT inside the ledger that was never in the vault, and withdraw it.
The team's post-mortem says this exact difference was not monitored at the time:

> "The internal systems of NEAR Intents had been monitoring the discrepancies of the origin chain and total NEAR-side token balances, but they did not monitor the discrepancies of the total balances of all users on NEAR Intents and the token balance of the Intents contract."
> ([post-mortem, 16 Oct 2026](https://x.com/AlexAuroraDev/status/2111124226962870770))

The team then added this check internally, with an automatic pause, and all affected users were made whole.
Vault Check is the **independent, public** version of that check: anyone can run it, with no keys, no funds and no indexer, and it replays the October incident from public chain state to show when it would have fired.

## Try it (no keys, no funds)

Requirements: Python 3.9+ and `make`. No packages to install (standard library only).

## How it works

- `vaultcheck/tokens.py` enumerates `intents.near.mt_tokens` (87,000+ ids, mostly NFTs) and keeps the fungible ones: `nep141:<contract>` and `nep245:<contract>:<inner id>`.
- `vaultcheck/scan.py` reads both sides at one block: `mt_batch_supply` on `intents.near` (50 ids per call), `ft_balance_of(intents.near)` on each NEP-141 contract, and `mt_batch_balance_of(intents.near, ...)` on each NEP-245 contract.
- `vaultcheck/alarm.py` classifies each token: `backed` (ledger <= vault), `standing` (an old gap that is not growing), `drift` (growing, below the threshold), `ALARM` (an unbacked gap grew by at least $1,000 since the baseline), `unverifiable` (one side cannot be read).
- `vaultcheck/reproduce.py` rebuilds every number offline from `data/`; `vaultcheck/report.py` and `vaultcheck/demo.py` write a single-file HTML report and the replay.
- `vaultcheck/rpc.py` is a small JSON-RPC client: archival `block_id` view calls, a shared rate limiter, retries on 429, and an on-disk cache so long scans resume.

### NEAR features used

| Feature | Where |
| --- | --- |
| NEP-245 `mt_supply`, `mt_batch_supply`, `mt_tokens` on `intents.near` | ledger side, token universe |
| NEP-141 `ft_balance_of`, NEP-245 `mt_batch_balance_of` / `mt_balance_of` | vault side |
| Archival view calls at a fixed `block_id` | replaying history, reproducible snapshots |
| `pa_is_paused({"key":"ALL"})` on `intents.near` | confirms the on-chain pause matches the post-mortem |
| Named accounts and contract-held balances | the whole check needs no keys and sends no transactions |

## Limits

- It detects one failure class: a ledger that owes more than the vault holds. It would **not** have caught the 2026 Rhea Lend loss (oracle manipulation) or the SWEAT Foundation loss (withdrawal-logic flaw); those need different controls.
- It is a monitor, not a guard: it raises an alarm after money starts to leak. The value is time to detection.
- NFT ids (`nep171`) are out of scope. The token universe is a snapshot (`data/universe.json`); tokens listed later need a refresh.
- USD values use a committed price snapshot from the public Intents token API; tokens without a price use a relative rule (alarm when the gap grows by 1% of the ledger).
- It publishes totals per token only. It does not publish per-account balances or attacker addresses.
